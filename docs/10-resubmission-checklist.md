# 10 — Submission readiness checklist

## Prepared in this correction pack

- [x] Corrected reports separate prototype source, hypotheses, plans and recorded evidence.
- [x] Human-centred problem draft, research forms, journey worksheet and alternatives prepared.
- [x] Historical AI provenance and unsupported sample outcomes corrected.
- [x] In-app review-page replacement and a shared evidence summary prepared.
- [x] Feedback/iteration record and technical test plan prepared.

These checked items describe files prepared, not files already installed in the local project, pushed to GitHub, deployed or submitted to RAale.

## Installation and technical checks

- [ ] Review and apply the correction pack to the actual project; resolve any changed-file conflicts.
- [ ] Run dependency installation, database setup on a disposable dataset, TypeScript/build and workflow tests.
- [ ] Verify both review-page routes, responsive display and print preview in a browser.
- [ ] Address baseline deployment risks, including fallback JWT secret, demo credentials and authorization checks.
- [ ] Record the tested build/commit and provide a controlled demo or redacted recording accessible to the evaluator.

## Design-thinking evidence

- [ ] Confirm Pathway A or B and record the supporting prior/fresh evidence.
- [ ] Add actual interviews/observations and consented/redacted evidence.
- [ ] Populate empathy maps and journey map from evidence, not assumed speech.
- [ ] Refine the problem statement and user stories from those findings.
- [ ] Preserve authentic AI interaction evidence; label any reconstruction and current retrospective work.
- [ ] Record the team's accepted/rejected alternatives and reasons.
- [ ] Test with at least three real people and record their actual roles, dates, tasks and feedback.
- [ ] Link important feedback to changes or reasoned non-changes and document actual retests.
- [ ] Update summary records in `data/project-review.json`, resolve checker findings and inspect links.
- [ ] Have a team member verify claims against original evidence; protect private participant data.

## Assessment and delivery

- [ ] Clarify the Review 2 completion label and any required percentage with the coordinator.
- [ ] Replace interim status wording only when the corresponding activities are genuinely complete.
- [ ] Confirm the repository's current branch has the reviewed files and evidence.
- [ ] Submit only after checking the report actually matches that repository version.

`node scripts/check-review-evidence.mjs --submission` is a useful minimum metadata gate, not an automated grade or proof that the activities happened. An honest incomplete progress report is preferable to a completed claim based on sample records.
